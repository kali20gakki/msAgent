# 仿真流水与 SIMD/SIMT 优化分析

使用本技能时，咨询和执行任务都必须先从 [msopprof 代码仓](https://gitcode.com/Ascend/msopprof) 读取 msopprof 与 msopprof simulator 的使用资料。先通过仓库 README 定位相关指南并读取正文，再回答工具用法或生成执行命令。

工具安装、环境配置、编译要求、参数、A2/A3/A5 与输入模式差异、采集和解析方法，均以读取到的对应版本正文为准。记录资料来源与版本。查询失败时查找本地相关工具或本地资料参考用法；缺少可靠说明时，分析已有数据并明确未核验部分，不能凭旧模板或记忆猜测用法。

用流水图定位耗时发生的位置，再用源码、指令和必要的补充证据选择优化技巧。既分析空泡，也分析持续忙碌却执行代价高的阶段；目标是缩短关键依赖链上的耗时。默认先交付 Markdown 分析报告和优化建议，再询问是否修改代码实施优化；代码修改以用户明确授权为前提。

## 确认输入与证据

完成资料查询后，确认当前工程、启动方式、产品线和具体 SoC、输入类型及已有数据；优先复用有效采集。记录 shape、dtype、核/线程配置、分块、源码与工具版本，保留实际命令、日志、退出状态、产物来源和精度结果。

按读取到的工具资料确定本次采集或解析方法，并识别流水、热点及原始指令数据。区分算子调用、核和子核，避免混用多次运行、汇总和单核结果。片段数据仅支持其覆盖范围内的结论，不能证明完整耗时或正确性。

从源码与启动接口识别 SIMD Tensor/寄存器 VF、独立 SIMT Kernel 或 SIMD 调用 SIMT VF，记录实际 `gridDim`、线程数和编译期最大线程数。`PUSHQ`、`VECTOR` 或 RVEC 泳道名称不能单独证明编程模型；AIC/AIV MIX 是核间协作维度，不等同于 SIMD/SIMT 混合编程。

## 分析顺序

共同的统计口径、证据边界和同步归因见 [流水分析参考](references/pipeline-analysis.md)。按当前代码选择优化参考，不同时加载无关模式的条目：

- SIMD Tensor、寄存器 VF 或矩阵计算：[SIMD 技巧与流水映射](references/simd-optimization-map.md)。
- SIMT Kernel、SIMT VF 或 SIMD/SIMT 混合编程：[SIMT 技巧与流水映射](references/simt-optimization-map.md)。混合工程按片段分别分析，跨阶段依赖仍用共同口径。

1. **确认数据语义**：结合编程模型区分仿真指令流水和上板流水。查看实际 `pid/tid/ph/name/args`，确认时间单位、指令泳道、同步事件、VF 边界及源码字段。
2. **选定范围**：按算子、调用实例、核/子核分别分析；优先选择包含多个完整数据块的窗口。明确启动、稳态、尾块、排空；无法确定块边界时只报告局部窗口。
3. **区分耗时形态**：先判断是阶段间空泡、阶段自身耗时高，还是启动/排空或核间尾部。空泡按区间并集统计，同步等待单列；忙碌阶段看指令次数、数据量、地址模式和源码热点，不因无空泡就停止分析。
4. **查看关键依赖链**：在同一窗口比较搬入、计算、写回的交集，追踪拖延下一阶段或最后完成者的生产者。新架构 VF 与内部 RVEC 不重复累加；SIMT 直接读写 GM 时可能没有 MTE 搬运，不能据此认定没有访存或缺少双缓冲。
5. **追溯依赖**：结合 SET/WAIT 的方向、事件 ID、重复出现顺序、Buffer 地址和源码确认生产者。C API 的 mutex 在某些 trace 中没有独立区间，可从原始指令 dump 的 GET_BUF/RLS_BUF、bufId 与计数补齐顺序证据；此时不填造等待时长。等待事件与空泡同时出现只是线索，还需说明依赖如何阻挡下一次执行。
6. **匹配技巧与补证**：按对应映射表选择最能解释当前关键耗时的候选，将“已观察事实”和“待验证原因”分开。Cache、带宽饱和、Bank 冲突、spill、分支发散或 occupancy 不能只凭流水外观定因；先补对应地址、资源报告或已有计数证据。
7. **给出最小实验**：每轮只改变一个可解释的设计点；需要联动 Buffer 与同步时说明改动组合。预先写出预期减少的 gap、指令、搬运或调度次数及可能增加的资源代价。Double Buffer、异步接口、Cache 策略等先核对目标架构与当前 API 前提，不把优化目录当成必做清单。

用户提供两份结果时，先核对逻辑工作量、精度和采集范围，再比较目标机制与完整仿真时序。减少冗余指令或搬运是合理优化，不要求物理指令数和流量始终不变，但要解释差异。热点 CSV 聚合时长不能直接相加作为算子耗时；仿真 wall time 或 trace span 不作为上板加速比。优化后重新判断瓶颈是否转移，不因覆盖率上升或局部 gap 缩短就宣称整体收益。

需要其他性能数据补证时，先依据所读工具资料确认数据含义与适用范围，使用已有数据或列出待采项，不自动将任务改成上板采集。不同重放或采样数据不能拼成同一条精确时间轴。

## 输出要求

每次分析都必须生成并保存一份 Markdown 分析报告，按任务规模组织，包含：

- 环境、A2/A3/A5 与具体 SoC、资料来源/版本、编程模型、输入、线程/核配置、命令、产物路径、采集完整性和精度验证状态。
- 关键耗时：核/子核、流水或 VF、区间、单位、指令/PC、同期其他流水及源码位置；说明属于空泡、忙碌阶段还是头尾/负载问题。
- 根因：观察证据、依赖关系、可信度；缺少的证据和待验证假设要分清。
- 建议按“现象 → 补证/依据 → 官方技巧 → 预期流水或指令变化 → 适用约束 → 最小对照实验”组织；无证据支持的收益不填数字。
- 已有对照时给出相同口径的前后数据；实测未出现预期变化时保留结果并检查采集和假设。

将分析报告保存到用户指定目录或本次实验目录，例如 `analysis-report.md`，在回复中提供报告路径或链接和关键结论，不能只在聊天中给出分析。

没有仿真环境时分析已有数据或提供可执行命令，明确未运行部分；没有 trace 或 dump 时不生成空泡数字。

## 确认并实施代码优化

交付分析报告后，若用户尚未授权代码修改，必须询问是否需要按报告建议修改算子、重新验证并生成 Markdown 优化对比报告；同时说明拟实施的设计点和受影响源码，使用户能基于报告作出选择。用户未明确同意前不修改算子，用户拒绝则结束于分析交付。用户已明确要求或在此前授权了相关代码优化时，沿用授权，不重复询问。

用户同意后：

1. 保留可复核的基线源码版本、输入、配置和采集产物，按已确认的建议实施最小改动；每轮实验遵循前述单一设计点和精度契约要求。
2. 重新编译、执行完整仿真和精度验证，在可比的输入、环境和采集范围下按相同统计口径比较；优化引起的分块、核/线程配置、指令和流量变化要说明原因。
3. 另存一份 Markdown 优化对比报告，例如 `optimization-comparison.md`，保留原分析报告。包含实际修改的文件与机制、前后环境和配置、关键流水/空泡/指令指标对照、精度结果、实际命令与日志及产物路径，并说明收益、退化或瓶颈转移及未验证项。

在回复中提供优化对比报告路径或链接和结果摘要。即使优化未改善、精度失败或无法完成复测，也要记录实际结果与具体原因；缺失指标标为未验证，不用预期数值代替实测，不将局部仿真变化表述为上板加速。

## 配套实测工程

[单/双缓冲案例工程](https://gitcode.com/Ascend/msopprof/tree/master/example/sample_simd_vf_double_buffer)由 msopprof 仓库的 `example/sample_simd_vf_double_buffer` 维护，不随本 Skill 分发。使用时从该仓库获取与实际工具配套的版本，或使用用户提供的本地 msopprof 案例路径，按案例 README 构建与校验。工程来自 asc-devkit，使用 `__simd_vf__`，包含两个场景、输入生成和精度校验。按工程说明先从基线形成诊断，再用双缓冲结果验证；对照已经充分重叠时转向忙碌阶段与剩余成本。该工程验证 SIMD 流水编排，不代表 SIMT 实测，也不意味着所有算子都应使用双缓冲。
